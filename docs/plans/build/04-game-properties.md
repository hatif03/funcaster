# Build 04: the Game Properties window and every option, exactly

Part of the [build specification](README.md). Status: plan, 6 November 2026. Everything here is grounded in a read of `core/catalog.js`, `server/arcade.cjs`, `server/party.cjs`, `public/party/host.js`, `schema-options.js` and `phone-admin.js` on 6 November. It corrects two assumptions in the earlier [xp-console-ui.md](../xp-console-ui.md) (seed and practice are not options; see section 2).

## 1. What the server gives us, and what it does not

| Fact | Consequence for the window |
| --- | --- |
| `optionSchema(id)` returns `[{key, label, choices: [[value, label], ...]}, ...]`. **No type, no default, no dependency, no help text.** | The window needs a **presentation layer** (section 3) that adds tab, control kind, order, help, visibility rules and value coercion. The schema stays the source of **choices and labels**. |
| Defaults come only from `matchSetup(game, requested, humans)` (`core/catalog.js:643-715`), which returns every key for every game, always. | The window derives each default by calling `matchSetup(id, {}, humans)` on the client; nothing is hard-coded twice. |
| The setup is **one flat object** `room.setup`, replaced wholesale by each `setup` event, and **ignored outside the lobby and results phases** (`party.cjs`, `onAdmin("setup")`). | Always send the full merged object: `{...state.setup, key: value}`. Never send a partial object. |
| `playlist` rides in the same `setup` event but is stored separately (`room.playlist`, `playlistIndex`), deduplicated, filtered to known ids and capped at 8. | The Playlists window sends `{...state.setup, playlist: [...]}`. |
| The raw `start` event has no acknowledgement and **silently does nothing** when `startReason` is not "Ready to play". `host.cmd {cmd:"start"}` instead returns `{error: startReason}`. | The shell starts through **`host.cmd`** so it can show the real reason in a message box. |
| `startReason` is built only in `startReason(room)` (`server/arcade.cjs:112-121`) and is the single source of truth for whether Start is allowed. | The status bar shows it verbatim (section 6). |
| There is **no server concept of presets** and no per-room persistence of the last setup (the kiosk idle timer resets it). | Presets and "My settings" are **client state** that emits `setup`; "My settings" is stored on the TV in `chonks.setup.<gameId>`. |
| The seed is generated by the server at `start()` (`party.cjs`, `room.match.seed`). | **There is no seed option.** The window can show the last round's seed read-only in Advanced. |
| Practice is a hard-coded 6-second phase for the three server games. | **There is no practice option.** |

## 3. The presentation layer: `public/os/option-ui.js`

A single module, `OPTION_UI`, keyed by option key. The renderer merges it with the schema of the selected game.

```js
// One entry per option key. `tab` is where it appears; `kind` is how it is drawn.
export const OPTION_UI = {
  mode:        { tab: 'play',     order: 10, kind: 'segments', label: 'Who plays', help: 'Auto uses Solo for one ready player and Multiplayer for two or more.' },
  cpuCount:    { tab: 'players',  order: 10, kind: 'segments', coerce: autoOrInt,
                 label: (g) => g === 'golf' ? 'Computer golfers' : 'Computer racers',
                 only: ['mario-kart', 'golf'], hideChoice: (g, v) => g === 'golf' && Number(v) > 4 },
  laps:        { tab: 'rules',    order: 10, kind: 'segments', only: ['mario-kart'] },
  holes:       { tab: 'rules',    order: 10, kind: 'segments', only: ['golf'] },
  golfMode:    { tab: 'rules',    order: 20, kind: 'select',   only: ['golf'] },
  course:      { tab: 'rules',    order: 30, kind: 'segments', only: ['golf'] },
  wind:        { tab: 'rules',    order: 40, kind: 'segments', only: ['golf'], coerce: windBool },
  skill:       { tab: 'players',  order: 20, kind: 'segments', only: ['golf'], enabledIf: (s) => s.cpuCount !== 0 },
  readyGolf:   { tab: 'advanced', order: 10, kind: 'segments', only: ['golf'] },
  turnSeconds: { tab: 'advanced', order: 20, kind: 'segments', only: ['golf'] },
  variant:     { tab: 'rules',    order: 10, kind: 'segments', only: ['fruit-ninja'] },
  bot:         { tab: 'players',  order: 30, kind: 'toggle',   enabledIf: botEnabled },   // see section 5
  interaction: { tab: 'rules',    order: 10, kind: 'toggle',   only: ['star-catch', 'bubble-burst', 'neon-drift'] },
  worldMode:   { tab: 'rules',    order: 10, kind: 'segments', only: ['shooting-range', 'island-flyover', 'alien-attack'] },
  language:    { tab: 'rules',    order: 20, kind: 'select',   only: ['drawing'] },
  theme:       { tab: 'rules',    order: 30, kind: 'select',   only: ['drawing'] },
  drawing:     { tab: 'rules',    order: 10, kind: 'segments', only: ['drawing'] },
  customWords: { tab: 'advanced', order: 30, kind: 'phoneText', only: ['drawing'], max: 2050 },
  tennisMode:  { tab: 'rules',    order: 10, kind: 'segments', only: ['table-tennis'] },
  winScore:    { tab: 'rules',    order: 20, kind: 'segments', only: ['table-tennis'] },
  rotation:    { tab: 'players',  order: 10, kind: 'segments', only: ['table-tennis', 'swordplay'] },
  pair:        { tab: 'players',  order: 20, kind: 'pair',     only: ['table-tennis', 'swordplay'], visibleIf: (s) => s.rotation === 'pick' },
};
```

Rules for the layer:

- **Coverage test:** for every game in the catalog, every key returned by `optionSchema(id)` must have an `OPTION_UI` entry (or the test fails). A game added later with an unknown key appears in a fallback **Advanced** group so it is never invisible.
- **`kind`:** `segments` (a row of large toggle buttons for up to 5 short choices), `select` (a drop-down for 4 or more or long labels), `toggle` (a check box for a two-value boolean choice), `pair` (two drop-downs fed by the ready players), `phoneText` (opens a text field **on the phone**, mirrored in the window).
- **`coerce`:** converts between the choice value and the wire value. Two known quirks: `cpuCount` uses the string `"auto"` for choice but the server wants `null` for auto and an integer otherwise (`host.js:471-472`); `wind` uses the strings `"off"` and `"on"` in the schema but `matchSetup` stores a boolean (`wind === true || wind === "on"`).
- **`only`:** the games the option applies to. It is redundant with the schema but lets the window keep a stable position for each option across games.
- The **labels shown come from the schema** (the existing wording), except where the layer overrides (computer racers versus golfers). The duplicate wordings that exist today ("Everyone who joins" in the old static select versus "Everyone ready" in the schema) disappear because the old static selects go away.

## 5. Dependencies and edge rules

| Rule | Behaviour |
| --- | --- |
| `bot` in Shooting Range and Alien Attack | The schema labels it "bot · shared modes". The control is **disabled with a tooltip** ("Helpers work in shared modes") while `worldMode` is `race` |
| `bot` in Slice Dojo | Labelled "Co-op helper blade"; **disabled** unless `variant` is `co-op` (the audit shows it is a co-op helper) |
| `cpuCount` | Clamped by `matchSetup`: golf allows at most 4 computer golfers, Kart Rush `8 - min(humans, maxHumans)`. The window shows the effective value in the summary ("5 racers: 3 players + 2 computer") from `state.match`/a local `matchSetup` call, not just the chosen number |
| `rotation = pick` | Shows the pair pickers. **Start is disabled with the reason "Pick two different players"** when both pickers have the same seat (the current page does this at `host.js:375-380`) |
| Multiplayer with one ready player | Start disabled; the reason is the server's `Waiting for 1 more ready player`; `mode: multiplayer` explains itself in help |
| `mode: solo` with several ready players | Allowed: **Next player** in turn (the server's `next-player`); the window shows a note "Players take turns" and the Players window has the *Next player* button |
| Remote screens (when enabled) | The server's `remoteReason` appears as the reason ("Waiting for Dev's screen to be ready", or the WebGL message) |

## 6. Start, status bar, and message boxes

- **Start enabled** if and only if `state.startReason === "Ready to play"` **and** the local checks above pass. Both conditions are shown, never silently.
- **Status bar text** is `state.startReason` unless a local check fails (then that message). Phase `lobby` and `results` only; in other phases the window is closed.
- **Starting uses `host.cmd`**:

```js
const seq = nextSeq();                         // integer >= 1, strictly increasing per session
socket.emit('host.cmd', { seq, cmd: 'start' }, (ans) => {
  if (ans?.error) messageBox({ icon: 'info', title: 'Not yet', text: ans.error });
});
```

  Replies seen: `"Wait until this round ends."`, the `startReason` string, `"Give it a moment."` (rate limit of 5 per second, handled by disabling Start for 400 ms after a press), `"This command has expired."` (a repeated `seq`), `"Room controls are not assigned to this phone."` (not applicable on the TV).
- **After a successful start** the window closes; the shell shows the loading window (section 8 of [03-shell-architecture.md](03-shell-architecture.md)).
- **Select and setup events:**
  - **Opening a game's icon emits `select {game}`** (only accepted in lobby or results), so phones and the party menu follow what the host is looking at, exactly as the old card click did.
  - **Each option change emits `setup`** with the full merged object, debounced 150 ms (a burst of D-pad presses sends one event). The server acknowledges `{ok:true}`; ignore errors silently except "Wait until this round ends."
  - **Cancel** closes the window and restores the previous `setup` snapshot taken when it opened (so abandoned experiments do not stick), then leaves the selected game as is.

## 7. Presets

Client constants in `OPTION_UI`'s companion `PRESETS`. Applying a preset emits `setup` with `{...state.setup, ...preset}`. **My settings** loads `chonks.setup.<gameId>`, written whenever a game starts.

| Game | Quick | Standard (the defaults) | Third preset |
| --- | --- | --- | --- |
| Kart Rush | laps 1, computer racers 0 | laps 1, auto | **Epic**: laps 3, computer racers 7 (Fill the grid) |
| Pocket Greens | holes 1, wind off | holes 3, stroke, classic, calm | **Full round**: holes 6, wind on, seeded course |
| Slice Dojo | variant co-op | co-op | **Versus**: variant battle |

If a game has no options beyond `mode`, **the preset row is not drawn**.

## 8. The window, exactly

### 8.1 Geometry (1x = 1280 by 720; scales with `--ui`, see [03-shell-architecture.md](03-shell-architecture.md) section 6)

| Part | Size at 1x |
| --- | --- |
| Window | 760 wide by 520 tall, centred; never larger than 92% of the viewport (the tab body then scrolls inside) |
| Title bar | 32 high; icon 20; title in the bold UI face; three buttons 26 square |
| Left task pane | 240 wide: backdrop image 240 by 135 on top, then the game's `verb` (18 px), `detail` (14 px, up to 4 lines), then groups |
| Right body | tab strip 36 high, tab page fills; page padding 16 |
| Bottom bar | 56 high: status text on the left (flexible), **Start** 140 by 40 (default button), **Cancel** 100 by 40 |

### 8.2 Markup and ARIA

```html
<section class="xp-window" role="dialog" aria-labelledby="gp-title" data-window="game-properties" data-game="mario-kart">
  <header class="xp-titlebar">...</header>
  <div class="gp-body">
    <aside class="xp-taskpane">
      <img class="gp-backdrop" alt=""><h2 id="gp-verb"></h2><p id="gp-detail"></p>
      <details class="xp-group" open><summary>Game tasks</summary>
        <button data-task="start">Start</button><button data-task="reset">Reset to defaults</button>
        <button data-task="rules">Rules of this game</button></details>
      <details class="xp-group" open><summary>Presets</summary><div role="radiogroup" aria-label="Presets">...</div></details>
    </aside>
    <div class="gp-main">
      <div role="tablist" aria-label="Game options">
        <button role="tab" aria-selected="true" aria-controls="gp-play" id="tab-play">Play</button> ...
      </div>
      <div role="tabpanel" id="gp-play" aria-labelledby="tab-play">...</div>
    </div>
  </div>
  <footer class="xp-statusrow"><p id="gp-status" role="status" aria-live="polite"></p>
    <button class="xp-default" id="gp-start">Start</button><button id="gp-cancel">Cancel</button></footer>
</section>
```

- Each `segments` control is `role="radiogroup"` with `role="radio"` buttons; each `select` is a custom list with `role="listbox"`; each `toggle` is `role="checkbox"`.
- Every focusable has `data-nav` (see the navigation spec) and a visible label.

### 8.3 Play tab content

1. **Who plays**: the `mode` segments.
2. **Summary line**, built from the setup: `"{laps} · {n} players · humans only · {preset name}"`, with the effective player counts.
3. **The player strip**: four seat chips (shape, colour, name, ready or waiting), the same chips as the tray, live from `state.players`.
4. A **hint** that changes with state: "Waiting for Dev to get ready", "Everyone is in".

### 8.4 Keyboard and remote behaviour

- `Left`/`Right` (or the D-pad) change the focused segment; `Up`/`Down` move between rows; `Tab` moves between tabs and the bottom buttons.
- **B** or **Escape** = Cancel (with the restore described above). **A** on Start = start. **Plus/minus** change a focused stepper.
- Default focus on open: the **Start** button if Start is enabled, otherwise the first control on the Play tab.
- Focus is trapped inside the window; on close it returns to the icon that opened it.

## 9. The phone mirror

The phone's party menu (`phone-admin.js`) renders every schema field as a plain `<select>` today and has no pair picker or playlist. v2:

- Use the **same `OPTION_UI` groups** (Play, Rules, Players, Advanced) as collapsible sections of one list; segments become big rows.
- Add the **pair picker** and the **Next player** action (host-only today).
- Send the same full-object `setup` event (via `host.cmd` with `cmd: "setup"` as the phone already does).
- Because both surfaces read one module, the **wording cannot diverge**.

## 10. Data bindings (what the window reads and writes)

| Reads from `state` | Used for |
| --- | --- |
| `game`, `setup`, `match` | Selected game, current options, effective counts |
| `players[]` (`slot`, `name`, `color`, `connected`, `ready`, `mode`, `status`) | The strip, the pair pickers, the tiers chips |
| `startReason` | The status bar and Start enablement |
| `options` | Present only in arcade rooms: `optionSchema(room.game)`; the window also imports `optionSchema` locally so it can draw any game before `select` lands |
| `phase` | The window exists only in `lobby` or `results` |
| `operatingMode`, `kioskStartsAt` | Kiosk replaces this window with the attract window |
| `maxPlayers`, `queueCount`, `locked`, `leaderboard` | Chips and the side panel |
| `remoteViews`, `screenPairings`, `seatViews`, `gate` | Remote readiness text |

| Emits | When |
| --- | --- |
| `select {game}` | Opening a game |
| `setup {...state.setup, ...changes}` | Any change, debounced 150 ms |
| `host.cmd {seq, cmd:"start"}` | Start |
| nothing | Cancel (it restores through `setup`) |
